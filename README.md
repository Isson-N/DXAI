# Контроль качества DXA-исследований

Сервис локально анализирует DICOM-изображения поясничного отдела позвоночника и проксимального отдела бедра. Для каждого изображения он определяет анатомическую область, наличие нарушения качества, вероятность нарушения и его тип. Результат выдаётся в CSV или XLSX; обработку можно запустить из командной строки или через локальный HTTP API.

Ниже приведены требования к запуску, интерфейсы, формат данных и измеренные характеристики текущей сборки.

## Возможности и ограничения

Сервис выявляет пять типов нарушений:

- неполное отображение поясничного отдела (`Некорректная укладка`);
- отклонение оси позвоночника более чем на 5°;
- посторонние предметы на снимке поясницы;
- неправильное положение или ротацию бедра (`Некорректная укладка`);
- неполную область интереса бедра.

Сервис сохраняет UID исследования и изображения, продолжает обработку после ошибки отдельного файла и формирует отдельный журнал ошибок. Одинаковые изображения внутри одного запуска распознаются один раз по хешу пикселей.

Ограничения:

- поддерживаются только поясничный отдел позвоночника и проксимальный отдел бедра;
- ранее нанесённая аппаратом разметка области интереса не проверяется;
- многокадровый монохромный DICOM обрабатывается по первому кадру;
- качество на аппаратах и типах изображений, отсутствовавших в обучающей выборке, не оценивалось;
- внешняя независимая проверка пока не проводилась;
- результат поддерживает контроль качества и не заменяет заключение специалиста.

Для текущей комбинации компонентов сводный macro-F1 на внешних фолдах, разделённых по исследованиям, составляет **≈ 0,689**. По отдельным нарушениям F1 равен: обрезка поясницы — 0,909; ось позвоночника — 0,455; посторонние предметы — 0,842; ротация бедра — 0,667; область интереса бедра — 0,571. Кластерный 95% доверительный интервал для их совместного macro-F1 пока не рассчитан: построчные внешние предсказания двух обновлённых компонентов не сохранились. Интервал 0,414–0,627 относится к прежней комбинации (macro-F1 0,546), а интервал 0,562–0,775 получен из агрегированных счётчиков без учёта группировки по исследованиям; ни один из них не является кластерным ДИ текущей сборки.

Сквозная проверка текущих весов на трёх DICOM (два исследования) завершилась без ошибок. Результаты CPU и CUDA в контейнере совпали по всем полям предсказания. В двух проверочных контейнерных прогонах на одной Tesla V100S загрузка моделей заняла 3,352–3,392 с, обработка набора — 0,611–1,543 с, максимальное время исследования — 0,532–0,772 с, пиковая выделенная память CUDA — 0,747 ГиБ. В более раннем прогоне сервиса без контейнера на том же GPU обработка набора заняла 5,976 с; на CPU сквозной запуск занял 58,18 с. Времена получены в разных прогонах, а запуск самого контейнера в них не включён. Малая техническая выборка не подтверждает производительность на 100 исследованиях.

## Системные требования и зависимости

Для рекомендуемого контейнерного запуска нужны:

- 64-битная Linux, macOS или Windows с WSL2;
- Git;
- Docker Engine с поддержкой `docker build` и bind mounts;
- Bash и утилита `realpath`;
- место для образа, Python-зависимостей, весов и результатов.

Минимальные значения RAM и числа ядер отдельно не измерялись. По умолчанию сервис работает на CPU. Для CUDA нужны совместимая NVIDIA GPU и драйвер; обычно используется NVIDIA Container Toolkit, на некоторых хостах возможен ручной проброс устройств. GPU не обязателен. Проверенная GPU-конфигурация: одна Tesla V100S 32 ГиБ; это описание испытания, а не минимальное требование. Четыре файла весов занимают около 143 МБ.

Контейнер построен на Python 3.12 и Debian Bookworm. Основные зависимости: PyTorch 2.8.0, torchvision 0.23.0, timm 1.0.29, NumPy 2.4.6, pydicom 3.0.2, pylibjpeg с декодерами JPEG/OpenJPEG и openpyxl 3.1.5. Полный список зафиксирован в [`requirements.txt`](requirements.txt). Для разработки пакет требует Python 3.11 или новее; аналитические зависимости перечислены в [`requirements-analysis.txt`](requirements-analysis.txt).

## Сборка контейнера

```bash
git clone https://github.com/Isson-N/DXAI.git
cd DXAI
bash docker/build.sh dxaqc:0.1.0
```

Сценарий устанавливает зафиксированные зависимости и включает четыре файла весов в образ. Перед сборкой убедитесь, что они присутствуют:

```bash
ls models/quality_cnn.pt models/spine_keypoints.pt \
   models/foreign_patch.pt models/hip_rotation_cnn.pt
```

Для Podman задайте `CONTAINER_ENGINE=podman`. Сборке нужен доступ к источнику базового образа и Python-пакетам; пакетный запуск после сборки выполняется с `--network none`.

## Руководство пользователя: пакетная обработка

Подготовьте каталог с DICOM-файлами произвольной вложенности либо ZIP-архив и запустите:

```bash
bash docker/run.sh /path/to/dicom_or.zip /path/to/results csv dxaqc:0.1.0
```

Аргументы по порядку:

1. существующий каталог или ZIP с входными данными;
2. каталог результатов, создаваемый при необходимости;
3. `csv` или `xlsx` (по умолчанию `xlsx`);
4. тег образа (по умолчанию `dxaqc:0.1.0`).

Результаты появятся в `results.csv` или `results.xlsx`, замечания и ошибки — в `errors.csv`. Вход монтируется только для чтения, сеть контейнеру недоступна.

Запуск на GPU:

```bash
DEVICE=cuda bash docker/run.sh /path/to/dicom /path/to/results xlsx dxaqc:0.1.0
```

На хосте, где контейнерный движок не передаёт CUDA через `--gpus all`, доступен явный проброс первого GPU и драйверной библиотеки:

```bash
CONTAINER_ENGINE=podman DEVICE=cuda GPU_MODE=manual \
  bash docker/run.sh /path/to/dicom /path/to/results xlsx dxaqc:0.1.0
```

Этот режим требует доступа к `/dev/nvidia0`, `/dev/nvidiactl`, `/dev/nvidia-uvm` и `/lib/x86_64-linux-gnu/libcuda.so.1` на хосте. При другом расположении библиотеки задайте `CUDA_DRIVER_LIB`. Для оценки времени после сборки запустите `bash docker/benchmark_gpu.sh /path/to/dicom dxaqc:0.1.0` с теми же переменными окружения.

Код завершения 0 означает, что пакетный запуск закончен и отчёты созданы. Ошибка отдельного изображения не останавливает пакет: строка получает `processing_status=Failure`, а причина попадает в `errors.csv`.

## Руководство по развёртыванию HTTP API

API предназначен для локальной доверенной среды. Он не имеет TLS, аутентификации, очереди заданий и управления параллельностью. Не публикуйте его во внешнюю сеть.

```bash
mkdir -p /path/to/results
bash docker/api.sh /path/to/input-root /path/to/results 8000 dxaqc:0.1.0
```

Вход монтируется только для чтения. При рабочей поддержке публикации портов контейнерным движком порт доступен как `127.0.0.1:8000`; в некоторых конфигурациях rootless Podman публикация порта недоступна и требуется настроенная сеть контейнеров. Для GPU добавьте `DEVICE=cuda` и, если нужен явный проброс, `GPU_MODE=manual`. Процесс работает на переднем плане, остановка — `Ctrl+C`. Для постоянного развёртывания запускайте сценарий под управлением systemd или другого менеджера процессов с политикой перезапуска и доступом через loopback либо защищённый обратный прокси.

Проверка готовности:

```bash
curl http://127.0.0.1:8000/health
```

После обновления кода или весов соберите образ с новым тегом, остановите старый процесс и запустите API с новым тегом. Каталог результатов расположен на хосте и сохраняется после удаления контейнера.

## HTTP API

Все ответы имеют `Content-Type: application/json; charset=utf-8`.

### `GET /health`

Успешный ответ `200`:

```json
{"status":"ok","model_version":"geometry+cnn+patch-1+hiprot"}
```

### `POST /predict`

Запускает синхронную обработку. Соединение остаётся открытым до завершения; идентификатор задания не означает фоновую очередь.

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H 'Content-Type: application/json' \
  -d '{"input":"study.zip","format":"csv"}'
```

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `input` | string | да | Относительный путь к каталогу или ZIP внутри входного корня |
| `format` | string | нет | `csv` по умолчанию либо `xlsx` |

Абсолютные пути, обратные слеши и выход через `..` за пределы входного корня отклоняются. Максимальный размер JSON — 65 536 байт.

Успешный ответ `200`:

```json
{
  "job_id": "6f7c...",
  "results_file": "/output/6f7c.../results.csv",
  "errors_file": "/output/6f7c.../errors.csv",
  "processed": 1,
  "failed": 0,
  "elapsed_seconds": 19.4,
  "rows": [{"path_to_study":"study/image.dcm","study_uid":"...","image_uid":"...","anatomical_region":"Поясничный отдел позвоночника","quality_class":0,"quality_prob":0.12,"violation_type":"","processing_status":"Success","time_of_processing":1.2}],
  "errors": []
}
```

Числа и пути в примере условные; в реальном ответе `rows` содержит по одной записи на каждый обработанный файл. `rows` и `errors` содержат те же записи, что сохранённые таблицы. Файлы создаются в `<output-root>/<job_id>/`. Пути в JSON относятся к контейнеру; на хосте каталог находится в `/path/to/results/<job_id>/`.

| Код | Причина |
| --- | --- |
| `400` | Некорректный JSON, путь или значение параметра |
| `404` | Маршрут либо входной набор не найден |
| `413` | Пустое тело, неверный `Content-Length` или тело больше лимита |
| `415` | `Content-Type` отличается от `application/json` |
| `500` | Непредвиденная ошибка; подробности в журнале сервера |

## Формат входных данных

Вход — каталог любой вложенности или обычный ZIP. Сервис рекурсивно и в детерминированном порядке просматривает файлы. DICOM определяется по расширению `.dcm`/`.dicom` либо по сигнатуре `DICM`.

Для обработки нужны `SOPClassUID` и пиксельные данные. По возможности читаются `StudyInstanceUID`, `SOPInstanceUID`, `PhotometricInterpretation`, `BitsStored`, `RescaleSlope` и `RescaleIntercept`. Поддержка сжатия зависит от декодеров pylibjpeg в образе. DICOMDIR, Structured Report, Presentation State и другие DICOM без изображения пропускаются и регистрируются в журнале. Не-DICOM файлы также пропускаются.

ZIP распаковывается во временный каталог; небезопасные пути за его пределы игнорируются. Исходные файлы не изменяются.

## Формат выходных данных

Основной отчёт содержит одну строку на прочитанное изображение, включая изображения с ошибкой модели:

| Поле | Тип и значения | Описание |
| --- | --- | --- |
| `path_to_study` | string | Относительный путь во входном наборе |
| `study_uid` | string | `StudyInstanceUID`, если доступен |
| `image_uid` | string | `SOPInstanceUID`, если доступен |
| `anatomical_region` | string | Поясничный отдел позвоночника или проксимальный отдел бедра |
| `quality_class` | integer | `0` — нарушений нет; `1` — найдено хотя бы одно |
| `quality_prob` | float | Вероятность нарушения, диапазон 0–1 |
| `violation_type` | string | Типы нарушений через `;`, пусто для нормы |
| `processing_status` | string | `Success` или `Failure` |
| `time_of_processing` | float | Время обработки изображения в секундах |

При `Failure` прогнозные поля пусты. CSV записывается в UTF-8 с заголовком; XLSX содержит лист `results` с теми же колонками.

`errors.csv` всегда создаётся:

| Поле | Описание |
| --- | --- |
| `path` | Относительный путь к проблемному файлу |
| `stage` | Этап: `discover`, `read` или `predict` |
| `message` | Причина ошибки или предупреждение |

## Модель, предобработка и постобработка

Решение объединяет четыре набора весов:

- `quality_cnn.pt` — многоголовая ResNet18 для области, общего качества и нарушений;
- `spine_keypoints.pt` — сеть точек тел Th12–L5 и состояний подвздошных гребней;
- `foreign_patch.pt` — ансамбль патч-классификаторов посторонних предметов;
- `hip_rotation_cnn.pt` — CNN положения и ротации бедра с предварительным обучением энкодера на синтетических проекциях КТ.

Предобработка:

1. Декодируются пиксели, применяются `RescaleSlope` и `RescaleIntercept`.
2. `MONOCHROME1` инвертируется с учётом `BitsStored`; цвет переводится в яркость усреднением трёх каналов; у многокадрового монохромного файла берётся первый кадр.
3. Интенсивность ограничивается перцентилями 0,5 и 99,5 и приводится к диапазону 0–1.
4. Изображение без искажения пропорций вписывается в квадрат 384×384. CNN получает нормированное изображение, лапласиан и маску заполненной области.
5. Левое бедро отражается горизонтально в ориентацию обучения.

Постобработка:

- область выбирается CNN при пороге 0,5;
- неполнота поясничной области определяется по состояниям подвздошных гребней;
- вероятность нарушения оси вычисляется из угла между крайними центрами позвонков, порог решения соответствует 5°;
- вероятность посторонних предметов — максимум по сетке патчей;
- остальные признаки сравниваются с порогами из файлов весов;
- `quality_class=1`, если порог прошёл хотя бы один тип нарушения;
- `quality_prob` — максимум общей вероятности CNN и вероятностей отдельных нарушений.

## Известные ошибки и их обработка

| Ситуация | Поведение и действие |
| --- | --- |
| Файл не является DICOM | Пропускается, `stage=discover`; удалять его не обязательно |
| DICOM без `SOPClassUID` или повреждён | `Failure`, `stage=read`; повторно экспортируйте файл |
| DICOM без пикселей | Пропускается с `stage=read`; для DICOMDIR/SR это ожидаемо |
| Неподдерживаемое сжатие | `Failure`; добавьте декодер или перекодируйте DICOM |
| Многокадровый монохромный DICOM | Берётся первый кадр, записывается предупреждение |
| Нет файлов весов | CLI возвращает код 2, если нет ни одной модели; API требует все четыре |
| CUDA недоступна при `DEVICE=cuda` | Проверьте драйвер и `--gpus all`; если движок не передаёт GPU, используйте `GPU_MODE=manual` при наличии указанных выше устройств и библиотеки |
| Нет прав записи в результаты | Выдайте текущему UID право записи в каталог хоста |
| API вернул `500` | Проверьте stderr/журнал контейнера |
| Неизвестный домен данных | Проведите ручную проверку и локальную валидацию |

Пустой `errors.csv` означает отсутствие зарегистрированных предупреждений и ошибок. Частичный результат пригоден для анализа: сверяйте `failed` и журнал, затем повторяйте исправленные файлы.

## Обучение и дообучение модели

Обучение не требуется для готового контейнера. Для воспроизведения нужны исходные DICOM, таблица меток, групповые фолды и ручная разметка ключевых точек; медицинские данные в Git не входят.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/pip install -r requirements-analysis.txt
.venv/bin/pip install -e ".[dev]"
.venv/bin/python tools/build_index.py
```

Основная CNN и модель ключевых точек:

```bash
.venv/bin/python training/train_baselines.py \
  --models b2 --epochs 30 --size 384 --device cuda \
  --min-specificity 0.8 --out experiments/my_run/baseline --final-model

.venv/bin/python training/train_keypoints.py \
  --annotations data/annotations/spine_points_annotator1.json \
                data/annotations/spine_points_annotator2.json \
  --epochs 150 --size 384 --device cuda \
  --out experiments/my_run/keypoints \
  --final-model models/spine_keypoints.pt
```

Скопируйте `experiments/my_run/baseline/b2/final_model.pt` в `models/quality_cnn.pt`. Для патч-модели сначала подготовьте данные с `training/build_foreign_patches.py`, затем запустите `training/train_foreign_patches.py --final-model models/foreign_patch.pt`. Синтетическое предобучение модели бедра собрано в [`training/drr_pipeline.sh`](training/drr_pipeline.sh).

При дообучении сохраняйте разбиение по исследованиям: кадры одного исследования не должны попадать одновременно в обучение и проверку. Пороги выбираются на внутренних OOF-прогнозах, итоговая оценка — на внешних фолдах. Геометрические аугментации не применяются, поскольку поворот, сдвиг и обрезка меняют целевые признаки качества. Полный протокол приведён в [`docs/validation.md`](docs/validation.md), инструкция по разметке — в [`docs/annotation.md`](docs/annotation.md).

После получения новых весов положите все четыре файла в `models/`, заново соберите образ и проверьте его на отложенной выборке.
