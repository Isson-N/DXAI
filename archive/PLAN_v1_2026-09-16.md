## 1. Задумка решения

### 1.1. Что строим
«Цифровой помощник рентгенолаборанта». По каждому изображению он отвечает на три вопроса:
1. **Что это?** Какая область (поясница / левое или правое бедро) и какая проекция.
2. **Годится ли снимок?** Класс 0/1 со скором уверенности (скор нужен для ROC-AUC).
3. **Что именно не так и где?** Список нарушений, для каждого — измерение (угол 6,9°,
   «верхний край кадра на 1,2 см ниже середины Th12», «поле снизу 2,1 см при норме 3 см»)
   и картинка, на которой это нарушение показано.

### 1.2. Ключевая идея: сначала анатомия, потом правила
Почти все критерии из п. 2.3 **геометрические и уже заданы числами**: 5°, 3 см, 2 см,
«половина Th12», «видны гребни подвздошных костей», «виден большой вертел». Поэтому:

```
DICOM ─► чтение и нормализация ─► область/проекция ─┬─► ПОЯСНИЦА ─► модель анатомии ─► измерения ─► правила ТЗ ─┐
                                                     │               (позвонки, гребни)  (угол, уровни)            │
                                                     │             └► классификатор артефактов/металла ───────────┤
                                                     │                                                             ├─► вердикт + скор ─► CSV/XLSX
                                                     └─► БЕДРО ────► модель анатомии ─► измерения ─► правила ТЗ ──┤                ─► оверлей (DICOM SC)
                                                                     (вертелы, шейка,    (поля в см,               │                ─► DICOM SR
                                                                      седалищная, ROI)    наличие структур)        │
                                                                   └► классификатор ротации (малый вертел) ────────┘
```

Почему гибрид, а не «одна сеть, которая выдаёт брак/не брак»:
- **Данных мало**, особенно по отдельным нарушениям. Сеть, которая учит «угол > 5°» только
  по бинарным меткам, потребует много примеров. Сеть, которая находит позвонки, учится на
  десятках размеченных снимков, а угол потом считается формулой.
- **Объяснимость.** ТЗ требует «объяснять, какое именно нарушение обнаружено» (разд. 1),
  а жюри — «клиническую логику» (разд. 4, п. 8.5). Измерение в градусах и сантиметрах
  объясняет себя само.
- **Визуализация почти бесплатна**: точки, оси и рамки уже есть — их остаётся нарисовать (п. 2.6).
- **Устойчивость к новым аппаратам.** Правила от производителя не зависят, переучивать
  нужно только детектор анатомии.

Там, где критерий плохо формализуется (металл и артефакты, «контур слегка деформирован
малым вертелом»), — обычные классификаторы. Их вывод объясняет Grad-CAM или бокс детектора.

End-to-end классификатор тоже делаем: он нужен как **бейзлайн** для MVP и сравнения
в презентации, а на финале — как запасной признак в ансамбле.

### 1.3. Принципы, о которых договориться с первого дня
- Разбиение данных **только по пациентам** (п. 8.1 — утечка).
- **Всё детерминировано**: сиды, порядок файлов, версии (п. 2.7).
- **Никаких необработанных исключений**: каждая ошибка → строка `Failure` и запись в лог (п. 2.7).
- **Ничего не уходит наружу**: веса внутри образа, интернет в рантайме не нужен (п. 3.2).
- **Каждое решение по модели — с числами и ДИ**, записанными в `NOTES.md` и трекер экспериментов.
- **Внешние данные — только в обучение**, метрики — только на данных организатора; у каждой внешней части
  есть абляция «с / без».

- **A ★ Шаблон по аппарату.** У одной версии ПО отчёт свёрстан одинаково → координаты окна
  со снимком фиксированы. Определяем шаблон по `Manufacturer`+`SoftwareVersions`+размеру кадра.
  Быстро и надёжно, но нужно подобрать шаблоны вручную.
- **B. Автоматический поиск.** Самая большая связная область «рентгеновской» текстуры:
  порог → морфология → крупнейший прямоугольник; или маленький детектор
  «окно снимка» (100–200 боксов разметки).
- **C. Работать по всему скриншоту.** Самый простой путь, но текст и графики отчёта мешают
  модели, и появляется риск «подсматривания»: модель научится читать T-критерий, а не качество.

### 5.5. Если на изображении есть цветная разметка аппарата (H3)
- [ ] Разделить каналы: «серый» снимок (R≈G≈B) и цветные линии (|R−G| или |G−B| > порога).
- [ ] Из цветной маски получить: рамку ROI бедра, линии межпозвонковых промежутков,
      границы тел позвонков. **Это готовая «нанесённая разметка»**, корректность которой
      просят проверить (п. 2.2).
- [ ] Для модели анатомии цветные линии убрать (inpainting `cv2.inpaint`), иначе модель
      будет искать линии, а не кости.

### 5.6. Если есть текст на изображении

## 6. Этап 3. Таксономия нарушений и формат выхода (неделя 1) [MVP]

### 6.1. Коды нарушений

**Утверждено организатором (разъяснения, вопрос 6)** — в `violation_type` пишутся ровно эти строки:

| Область (`anatomical_region`) | Значение `violation_type` | Колонка в `разметка.xlsx` | Внутренние проверки (коды ниже) |
|---|---|---|---|
| Поясничный отдел позвоночника | Некорректная укладка | «корректная укладка» | `SPINE_UPPER_LEVEL`, `SPINE_LOWER_LEVEL` |
| Поясничный отдел позвоночника | Не выравнена ось позвоночника | «правильно выравнена ось (до 5)» | `SPINE_TILT` |
| Поясничный отдел позвоночника | Присутствуют посторонние предметы | «посторонние предметы…» | `SPINE_FOREIGN_BODY` |
| Проксимальный отдел бедра | Некорректная укладка | «позиционирование/ротация» | `HIP_ANATOMY_INCOMPLETE`, `HIP_ROTATION_OVER`, `HIP_ROTATION_UNDER` |
| Проксимальный отдел бедра | Некорректная область интереса | «корректности области интересов» | `HIP_ROI_MARGIN` |

Несколько нарушений — через `;`, нет нарушений — пустая строка. Коды ниже остаются
**внутренними** (для правил, отладки и оверлея); в ответ они сворачиваются в строки выше.
Меток для внутренних кодов в разметке нет — только для итоговых строк.

Черновик внутренних проверок:

| Код | Область | Блок | Критерий (п. 2.3) | Норма |
|---|---|---|---|---|
| `SPINE_UPPER_LEVEL` | поясница | укладка | верхний уровень — половина тела Th12 | видна ≥ половины Th12 |
| `SPINE_LOWER_LEVEL` | поясница | укладка | внизу видны верхние края подвздошных костей | оба гребня в кадре |
| `SPINE_TILT` | поясница | ось | наклон оси позвоночника | ≤ 5° |
| `SPINE_FOREIGN_BODY` | поясница | артефакты | посторонние предметы, металл, выраженные артефакты | нет |
| `HIP_ANATOMY_INCOMPLETE` | бедро | укладка | видны большой вертел, шейка, седалищная кость | все три |
| `HIP_ROTATION_OVER` | бедро | ротация | конечность переротирована: контур гладкий, малый вертел не деформирует контур | контур слегка деформирован |
| `HIP_ROTATION_UNDER` | бедро | ротация | конечность недоротирована: малый вертел слишком большой | малый вертел едва виден |
| `HIP_ROI_MARGIN` | бедро | область интереса | поля до краёв ≥ 3 см сверху/снизу, ≥ 2 см сбоку | выполнено |

Возможные дополнительные (если организатор включит или они будут в разметке):
`SPINE_ROI_MARKUP` (межпозвонковые линии не в промежутках, неверная нумерация позвонков),
`HIP_ROI_MARKUP` (neck box не на шейке), `HIP_FOREIGN_BODY`, `UNREADABLE` / `LOW_QUALITY`.

### 6.2. Иерархия
```
область ─┬─ укладка (уровни / анатомия в кадре)
         ├─ ось / ротация
         ├─ артефакты
         └─ разметка / область интереса
```
В презентации это слайд «таксономия» (разд. 4). Уровень «блок» пригодится, если
по отдельным кодам будет слишком мало примеров: метрики можно показывать по блокам.

### 6.3. Несколько нарушений сразу
- Задача **мультилейбл**: у каждого кода своя вероятность и свой порог.
- `quality_class = 1`, если сработал хотя бы один код.
- `violation_type` — коды через `;`, в фиксированном порядке (как в таблице 6.1);
  для годного снимка — пустая строка (или `none`, если так скажет организатор).
- Метрики: macro-F1 по кодам, F1 и ROC-AUC для каждого кода отдельно (п. 8.4).

## 7. Этап 4. Валидация и метрики (неделя 2) [MVP]

**Цель:** честные числа, которые совпадут с тем, что организатор получит на закрытом тесте.

### 7.1. Разбиение
- [ ] Группа — **исследование (имя папки)**: `PatientID` в данных анонимизирован. Дубли
      одного изображения внутри исследования схлопнуть до одного (`data/index/images.csv`),
      иначе они попадут и в train, и в val. Почти-дубли между исследованиями (повторные
      исследования одного пациента) поискать perceptual hash.
- [ ] ★ `sklearn.model_selection.StratifiedGroupKFold` (5 фолдов), стратификация по
      «область × есть нарушение»; редкие коды проверить вручную, чтобы попали в каждый фолд.
- [ ] **Holdout 15–20%** отложить один раз и не трогать до этапа 12.
- [ ] **Внешние и синтетические данные** добавляются только в обучающую часть каждого фолда.
      В валидацию, holdout и подбор порогов они не попадают. В логах эксперимента — какие внешние наборы
      и сколько примеров использованы.
- [ ] Если несколько аппаратов — отдельно посмотреть метрики «обучили на одном, проверили
      на другом» (для раздела «ограничения»).

### 7.2. Модуль метрик `dxaqc/metrics.py`
Для каждого среза (всё / поясница / бедро / каждый код):
- чувствительность (recall класса 1), специфичность, balanced accuracy, F1;
- ROC-AUC и PR-AUC по непрерывному скору;
- macro-F1 по кодам нарушений (`f1_score(Y, Ŷ, average="macro")` на матрице индикаторов);
- для вспомогательных моделей: Dice и IoU (маски), ошибка ключевых точек в пикселях и мм,
  ошибка угла в градусах;
- доля успешно обработанных файлов, время на изображение и исследование (среднее, p95, max).

### 7.3. Доверительные интервалы
- [ ] ★ Кластерный бутстрэп: ресэмплируем **пациентов** с возвращением, 2000 повторов,
      перцентильный интервал 2,5–97,5%.
- [ ] Для AUC можно сверить с методом DeLong; для чувствительности и специфичности
      при малых n — интервал Уилсона.
- [ ] В отчёте формат: `F1 = 0,84 (95% ДИ 0,79–0,88)`.

Набросок:
```python
def cluster_bootstrap(df, metric_fn, group="patient", n=2000, seed=0):
    rng = np.random.default_rng(seed)
    groups = df[group].unique()
    by_group = {g: idx for g, idx in df.groupby(group).indices.items()}
    vals = []
    for _ in range(n):
        sample = rng.choice(groups, size=len(groups), replace=True)
        idx = np.concatenate([by_group[g] for g in sample])
        vals.append(metric_fn(df.iloc[idx]))
    return np.nanpercentile(vals, [2.5, 97.5])
```

### 7.4. Выбор порогов
- [ ] Пороги подбираем на **out-of-fold** предсказаниях (объединение валидаций 5 фолдов).
- [ ] Цель — максимум F1 по коду (у жюри приоритет F1 и ROC-AUC). Отдельно показать
      точку «высокая чувствительность» (контроль качества: лучше лишний раз показать снимок
      врачу, чем пропустить брак) — это аргумент для питча.
- [ ] Для правил с порогами ТЗ (5°, 3 см, 2 см) порог **не подгонять** — он клинический.
      Подгоняется только допуск на погрешность измерения, и это нужно явно описать.

Данные: TotalSegmentator v2 (1228 КТ, маски позвонков, крестца, тазовых и бедренных костей, CC BY 4.0);

- [ ] **Кадрирование как у аппарата:** поясница — поле ~180 мм шириной от середины Th12 до гребней;

### 8.1В. Ручная разметка — только для того, что не закрылось
Ниже — прежняя схема ручной разметки (CVAT). Применять точечно: например, если на данных организатора
не хватает точек малого вертела или гребней после 8.0–8.1Б.

### 8.1. Инструмент
- ★ **CVAT** (MIT), поднимается локально в Docker, поддерживает точки, скелеты, боксы, полигоны,
  экспорт в COCO keypoints и YOLO. Умеет предразметку моделью SAM.
- Альтернатива — **Label Studio** (Apache-2.0), проще развернуть, но с точками и скелетами
  работать менее удобно.

### 8.2. Схема разметки

**Поясница** (скелет из точек, чтобы экспорт был в формате COCO keypoints):
- для каждого позвонка Th12, L1–L5: 4 угла тела (верх-лево, верх-право, низ-лево, низ-право);
  центр считается из углов;
- 2 точки: верхние точки гребней подвздошных костей, левая и правая;
- флаг видимости у каждой точки (`v=0` не в кадре, `v=1` частично закрыт, `v=2` виден) —
  **важно**: «Th12 не в кадре» — это полезная информация, а не пропуск;
- боксы: металл и посторонние предметы.

Упрощённый вариант, если времени мало: только центры тел позвонков (6 точек) + 2 гребня.

**Бедро:**
- точки: вершина большого вертела, центр головки, 2 точки по краям самой узкой части шейки,
  вершина малого вертела, 2 точки ширины диафиза под малым вертелом, нижняя точка
  седалищного бугра;
- боксы: большой вертел, малый вертел, шейка, седалищная кость; ROI аппарата, если его
  не удалось достать по цвету;
- (по возможности) полигон контура бедренной кости — для сегментации и анализа контура.

### 8.3. Объём и отбор
- Старт: ~150 изображений на область; затем «активная» доразметка: снимки, на которых
  модель ошибается сильнее всего.
- Отбор: все классы нарушений + пограничные случаи (угол 4–6°, «едва видны гребни»).
- 10% снимков размечают двое → согласие (среднее расстояние между точками, ICC для угла).
  Это же — «потолок» точности модели для слайда.

### 8.4. Ускорение разметки
- Предразметка SAM / MedSAM в CVAT (контур кости одним кликом).
- После первых 50–100 снимков — предразметка собственной моделью, человек только поправляет.

### 8.5. Инструкция разметчика
Одна страница с картинками: как ставить каждую точку, что делать при сколиозе,
переходном позвонке (LSTV), металле. Опираться на методические рекомендации организатора
(разделы 2.6, 2.7) и атлас ISCD (`data/materials.md`, п. 2).

### 8.6. Порядок обучения моделей с внешними данными
1. **Бейзлайн** «норма / нарушение» на данных организатора (без внешних) — точка отсчёта для всех абляций.
2. **Область** (поясница / бедро) — правило + маленький классификатор; внешние рентгенограммы и синтетика
   добавляют разнообразия для случая других размеров в закрытом тесте.
3. **Модели анатомии:** предобучение на AASCE/VertebraeKeypoints50 и синтетике → дообучение на масках
   `kaggle_dexa_osteo` → проверка на данных организатора (глазами + согласие с классической геометрией).
4. **Модели нарушений** (независимые): обучение на данных организатора + синтетика по нарушениям, прошедшим
   критерий 8.1А; посторонние предметы — предобучение на object-CXR.
5. **Итоговый `quality_prob`** — калибровка и комбинация на OOF данных организатора (раздел 12), без внешних данных.
6. **Абляции** для презентации: бейзлайн / + геометрия / + внешние метки анатомии / + синтетика / + object-CXR,
   всё с 95% ДИ.

## 10. Этап 7. Поясничный отдел: все проверки (недели 4–7) [F]

### 10.1. Базовая модель анатомии поясницы
Нужно получить: положения тел Th12–L5 (центры и/или углы) и верхние точки гребней.

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A ★ Heatmap-регрессия точек** | U-Net / HRNet-подобная сеть выдаёт карту «тепла» для каждой точки; координата = argmax или soft-argmax | точность субпиксельная, мало данных нужно, лицензии чистые | нужно самим написать лосс, декодирование, оценку видимости |
| **B. YOLO-pose** (Ultralytics) | один позвоночник = объект со скелетом из N точек | очень быстро стартовать, есть видимость точек | лицензия **AGPL-3.0** (см. раздел 17); модель рассчитана на людей, мелкие точки хуже |
| **C. Детекция позвонков + точки внутри** | детектор боксов на каждый позвонок (RT-DETR / Faster R-CNN), классы Th12…L5 или порядок снизу вверх | наглядно, естественно считать позвонки | нумерация — отдельная проблема (переходные позвонки) |
| **D. Сегментация** | маска каждого позвонка или всего столба (segmentation_models_pytorch) | даёт контуры для визуализации, ось = главная ось маски | разметка полигонов дороже |

Рекомендация: **A для точек + D (маска столба, по желанию) для визуализации**.
Если нужно «вчера» — B для MVP, затем переход на A (или купить или обосновать AGPL).

Практика:
- вход 512×512 или 768×768 с сохранением пропорций; сигма гауссианы 2–4 px на выходном разрешении;
- для невидимых точек (`v=0`) карта нулевая + отдельная голова «видимость» (BCE);
- предобучение энкодера на ImageNet (timm), по желанию — на открытых AP-рентгенограммах
  позвоночника (AASCE, BUU-LSPINE, раздел 18), потом дообучение на DXA.

### 10.2. `SPINE_TILT` — наклон оси
- Ось: прямая через центры тел **L1–L4** (именно по ним считается МПКТ), метод — МНК или
  RANSAC (устойчиво к одному ошибочному центру).
- Угол = угол между осью и вертикалью изображения (направлением сканирования).
- Вердикт: `angle > 5°`. Учесть погрешность: если оценка ошибки угла по валидации ±0,8°,
  зона 4,2–5,8° — «сомнительно», в расширенном отчёте флаг `borderline`.
- Альтернативы для сравнения:
  - главная ось маски позвоночного столба (PCA по пикселям маски);
  - классика без нейросети: вертикальная проекция яркости по полосам → центр столба
    в каждой полосе → прямая (быстрый бейзлайн, полезен для слайда «сравнение подходов»);
  - прямая регрессия угла CNN (не рекомендуется: хуже объясняется).
- Отдельно подумать про **сколиоз**: ось через центры и «наклон» — не одно и то же. Если
  в методичке организатора есть уточнение, следовать ему; иначе — угол прямой L1–L4 и
  отдельная пометка `scoliosis_suspected`, если центры сильно отклоняются от прямой.
- Проверка: пример из ТЗ, рис. 2 (1,6° — норма, 6,9° — брак) — модель должна выдавать близкие числа.

### 10.3. `SPINE_UPPER_LEVEL` — половина тела Th12
- Th12 нужно **пронумеровать**. Варианты:
  - **★ снизу вверх от таза**: гребни подвздошных костей обычно на уровне L4–L5 → нижний
    позвонок над крестцом = L5 → считаем вверх до Th12;
  - по рёбрам: Th12 — последний позвонок с ребром (рёбра видны на DXA не всегда);
  - сеть сразу предсказывает классы Th12…L5 (вариант C из 10.1).
- Вердикт: верхний край кадра должен быть не ниже середины тела Th12, то есть
  `y_top_frame ≤ (y_top_Th12 + y_bottom_Th12)/2`. Если Th12 не найден вообще — нарушение.
- Риски: переходные позвонки (LSTV — 6 поясничных или сакрализация L5), сильный сколиоз.
  В отчёте — уверенность нумерации; такие случаи вынести в «ограничения».

### 10.4. `SPINE_LOWER_LEVEL` — гребни подвздошных костей
- Точки верхних краёв гребней (или маска подвздошных костей в нижней части кадра).
- Вердикт: обе точки видимы и лежат внутри кадра с запасом в N пикселей от нижнего края;
  если видна только одна сторона — уточнить у организатора, брак ли это (вопрос 19).
- Бейзлайн без точек: классификатор на нижней полосе кадра «гребни видны / не видны».

### 10.5. `SPINE_FOREIGN_BODY` — посторонние предметы и артефакты

| Вариант | Как | Когда хорош |
|---|---|---|
| **A ★ Классификатор** | бинарная сеть на весь кадр или на полосы; Grad-CAM показывает, где | есть ≥ 50–100 примеров |
| **B. Детектор** | боксы металла (RT-DETR / Faster R-CNN из torchvision) | размечено ≥ 100–200 боксов; даёт точную визуализацию |
| **C. Классика** | металл на DXA — очень плотные компактные объекты с резкими краями: порог по верхним перцентилям яркости → связные компоненты → фильтр по размеру, форме, контрасту к окружению | как признак и как объяснение; без обучения |
| **D. Детекция аномалий** | PatchCore / PaDiM (anomalib) обучаются **только на годных снимках** | нарушений мало; ловит «что-то необычное» |

Рекомендация: **A + C** (скор классификатора + признаки классики), на финале — **B**, если
хватает разметки, для красивой визуализации. D — эксперимент, если примеров брака очень мало.
Отличать от «внутренних» объектов (металлоконструкции, кальцинаты аорты, остеофиты) —
уточнить у организатора, считаются ли они нарушением качества или только поводом
исключить позвонок.

### 10.6. Корректность разметки аппарата на позвоночнике (если есть H3 и если входит в задачу)
- Межпозвонковые линии аппарата vs промежутки, найденные моделью: отклонение по вертикали в мм.
- Нумерация аппарата (L1–L4) vs нумерация модели: сдвиг на позвонок — частая ошибка
  (о ней говорят в митапе НПКЦ ДиТ, `data/materials.md`, п. 8, 2:09–2:16).
- Боковые границы ROI позвонков vs контур тела позвонка.

## 11. Этап 8. Проксимальный отдел бедра: все проверки (недели 4–7) [F]

### 11.1. Базовая модель анатомии бедра
Нужно: большой вертел, шейка (узкая часть), головка, малый вертел, седалищная кость,
контур бедренной кости.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A ★ Heatmap-точки (как 10.1)** | единый код с поясницей | для «видна ли структура целиком» точки дают меньше, чем боксы |
| **B. Детектор боксов** (RT-DETR / Faster R-CNN) по 4–5 классам | «структура в кадре / обрезана» проверяется геометрией бокса | меньше информации о форме |
| **C. Сегментация бедренной кости и таза** (U-Net, smp) | контур нужен для ротации (11.3) и визуализации | дороже разметка (но есть SAM-предразметка) |

Рекомендация: **A или B для структур + C для контура бедра**. Опыт из литературы: U-Net
на DXA бедра даёт Dice ~0,95 на 555 снимках (Chu et al., 2026, раздел 18) — сегментация
бедра на DXA решается хорошо.

### 11.2. `HIP_ANATOMY_INCOMPLETE`
- Для каждой из трёх структур: найдена ли и не касается ли бокс или точки края кадра.
- Вердикт: нарушение, если хотя бы одна не видна или обрезана; в `violation_type`
  можно дописать, какая именно (в расширенном отчёте).

### 11.3. `HIP_ROTATION_OVER` / `HIP_ROTATION_UNDER`
Клинический смысл (ТЗ, рис. 5; ISCD): при правильной внутренней ротации 15–25° малый
вертел **едва виден** и слегка деформирует медиальный контур. Не виден совсем → переротация,
большой → недоротация.

| Вариант | Как | Плюсы / минусы |
|---|---|---|
| **A ★ Классификатор по кропу** | кроп вокруг области малого вертела (по найденным точкам шейки и диафиза), 3 класса: норма / over / under | прямо учится на метках эксперта; кроп убирает лишнее |
| **B. Геометрический признак** | из маски бедра: площадь или ширина выступа малого вертела относительно ширины диафиза; кривизна медиального контура ниже шейки | объяснимо («выступ 2 мм при норме 3–8 мм»), но нужна маска |
| **C. Порядковая регрессия** | одно число «степень ротации»: under < норма < over, два порога | естественный порядок классов, пороги подбираются по OOF |
| **D. Классификатор на весь снимок** | как бейзлайн | хуже объясняется |

Рекомендация: **A + признаки из B** (конкатенация в «голову» или стекинг) и C как вариант
для сравнения. Для визуализации — контур и подсвеченный малый вертел.
Подсказка из литературы (ISCD): очень большой малый вертел при недоротации называют
«Pike's Peak sign» — полезно для слайда.

### 11.4. `HIP_ROI_MARGIN` — поля 3 см / 2 см
Шаг 1. **Где область интереса:**
- если есть цветная разметка аппарата (H3) — рамка ROI из цветной маски (5.5) ★;
- иначе — ROI строится по анатомии так, как его ставит аппарат (total hip: головка,
  шейка, вертельная и межвертельная зона) из маски или боксов.

> **Обновление 16.09.2026.** ROI аппарата на снимках нет → Шаг 1 только по анатомии.
> Размер пикселя организатор назвал: 1,05 мм по Y и 0,6 мм по X. Но у 89 снимков поясницы
> `ExposedArea / размер` = 0,600 × 0,606 мм, а диафиз бедра (~43 пикселя) при 0,6 мм = 26 мм
> (норма), при 1,05 — 45 мм. Похоже, картинки уже пересчитаны на квадратный пиксель ~0,6 мм.
> До ответа организатора: размер пикселя — параметр конфига, пороги 3 см и 2 см проверить на разметке
> (какой вариант лучше разделяет «Некорректная область интереса»), варианты 2–5 ниже не нужны.

Шаг 2. **Пиксели → сантиметры.** По гипотезе H2 PixelSpacing может не быть.

| Вариант | Как | Надёжность |
|---|---|---|
| **1 ★ Тег** | `PixelSpacing` / `ImagerPixelSpacing`, если есть | высокая |
| **2. Таблица калибровки по аппарату** | размер пикселя фиксирован для модели аппарата, режима скана и размера кадра: берём из файлов, где тег есть, из документации аппарата или у организатора | высокая, если режимы стандартные |
| **3. Приватные данные** | у Hologic в приватных тегах лежат данные скана (размеры поля, разрешение) — разобрать | зависит от аппарата |
| **4. Анатомический масштаб** | средняя ширина шейки бедра / диафиза у взрослых → оценка мм/пиксель | низкая (±15–20%); только как запасной вариант с флагом |
| **5. Учиться напрямую** | классификатор «поля достаточны / нет» по экспертной метке + относительные размеры (поле / ширина шейки) | не требует калибровки, но хуже объясняется |

Рекомендация: **1 → 2 → 3 → 4** по цепочке, какой доступен; 5 — как контрольная модель
и для сравнения. В отчёте всегда указывать, каким способом получены сантиметры.

Шаг 3. **Вердикт:** `top ≥ 3 см`, `bottom ≥ 3 см`, `lateral ≥ 2 см` (сторона зависит от бедра,
ТЗ, рис. 6 — уточнить у организатора, какая именно боковая сторона и считается ли медиальная).

### 11.5. Корректность разметки аппарата на бедре (если H3 и входит в задачу)
- Neck box аппарата пересекает шейку перпендикулярно её оси и не заходит на большой вертел
  и головку; сравнить с осью шейки из модели (угол, смещение).
- Средняя линия бедра аппарата vs ось диафиза из маски.

## 12. Этап 9. Итоговый вердикт, пороги, мультилейбл (недели 6–7) [F]

- [ ] Для каждого кода — **непрерывный скор** `s_k ∈ [0, 1]`:
  - для правил: гладкая функция от «насколько нарушен порог» с учётом погрешности,
    например `sigmoid((angle − 5°)/σ_angle)`, где σ — ошибка угла на валидации;
  - для классификаторов — калиброванная вероятность (temperature scaling или изотоническая
    регрессия на OOF).
- [ ] Итоговый скор брака: ★ `1 − Π(1 − s_k)` («хотя бы одно нарушение») или логистическая
      регрессия по `s_k` на OOF; сравнить по ROC-AUC.
- [ ] Бинарный вердикт: порог итогового скора по OOF F1; коды — каждый со своим порогом.
- [ ] Согласованность: если `quality_class = 0`, `violation_type` пуст, и наоборот.
- [ ] **Сравнение вариантов** для презентации (все — с ДИ, на одних и тех же фолдах):
  1. end-to-end классификатор (бейзлайн MVP);
  2. гибрид «анатомия + правила + классификаторы»;
  3. ансамбль 1 + 2;
  4. абляции: без калибровки мм, без предобучения, разные разрешения входа.
- [ ] **Анализ ошибок**: таблица FP/FN с превью; разрез по аппарату, области, коду,
      «пограничным» измерениям; 5–10 характерных случаев сохранить для слайдов.

## 13. Этап 10. Сервис, API, контейнер (недели 5–8) [F]

### 13.1. Архитектура приложения
```
            ┌──────────── API (FastAPI) ────────────┐
 zip ─────► │ POST /v1/jobs  → job_id               │
            │ GET  /v1/jobs/{id}         статус      │
            │ GET  /v1/jobs/{id}/result  csv|xlsx    │──► очередь задач (1 воркер на GPU)
            │ GET  /v1/jobs/{id}/series  zip серий   │           │
            │ GET  /health, /version                 │           ▼
            └────────────────────────────────────────┘   pipeline: read → region → models
 CLI: dxaqc predict --input archive.zip --output out/            → rules → report → viz
```
- ★ FastAPI + фоновый воркер в том же процессе (очередь `asyncio` или `concurrent.futures`),
  задачи хранятся в папке `jobs/{id}/`. Для конкурса этого достаточно; Celery или Redis не нужны.
- Модели загружаются **один раз** при старте, прогрев на фиктивном изображении.
- CLI и API вызывают один и тот же `Pipeline.run(archive)` — поведение одинаковое.
- Запись xlsx — `openpyxl` (или `pandas.to_excel`), csv — UTF-8.

### 13.2. Устойчивость (п. 2.7)
- [ ] Обработчик на уровне файла, изображения и исследования; тайм-аут на изображение
      (например, 60 с), чтобы одно зависание не сорвало ≤ 3 мин на исследование.
- [ ] Логи в JSON (`structlog` или стандартный `logging`), отдельный `errors.csv` в результате.
- [ ] Набор «плохих» файлов в `tests/fixtures/`: обрезанный DICOM, не-DICOM с расширением `.dcm`,
      пустой zip, zip в zip, JPEG 2000 / JPEG-LS, `MONOCHROME1`, RGB, multi-frame, без
      `StudyInstanceUID`, без пикселей (SR-объект), > 3 изображений в исследовании,
      неизвестная область, кириллица и пробелы в путях.
- [ ] Цель тестов: пайплайн никогда не падает, у каждого входного файла есть строка
      или запись в `errors.csv`.

### 13.3. Контейнер (п. 3.2)
- [ ] Базовый образ — с **точным тегом и digest**, например официальный `pytorch/pytorch:<версия>-cuda12.x-cudnn9-runtime`
      или `nvidia/cuda:12.x-runtime-ubuntu24.04` + uv.
- [ ] Зависимости из `uv.lock`; системные пакеты с версиями.
- [ ] Веса внутри образа (`COPY weights/`), переменные `HF_HUB_OFFLINE=1`, `TORCH_HOME` на
      локальную папку — **никаких скачиваний при запуске**.
- [ ] Проверка: `docker run --network none …` проходит весь тестовый архив.
- [ ] `build.sh` (сборка, тег с версией) и `run.sh` (режимы `api` и `cli`, флаг `--gpus all`,
      монтирование папок входа и выхода); запуск без GPU — автоматически на CPU.
- [ ] Пользователь в контейнере — не root; порт API — параметр.

### 13.4. Воспроизводимость
- [ ] `torch.use_deterministic_algorithms(True)`, `torch.backends.cudnn.benchmark = False`,
      `CUBLAS_WORKSPACE_CONFIG=:4096:8`, фиксированные сиды.
- [ ] Сортированный обход файлов; одинаковая библиотека ресайза в обучении и инференсе.
- [ ] Тест: два прогона → идентичные csv (кроме `time_of_processing`).

### 13.5. Скорость
- Ожидание: ~0,1–1 с на изображение на H200 для 2D-сетей такого размера — с огромным
  запасом до 3 минут. Узкие места скорее в чтении и распаковке, чем в сети.
- ONNX или TensorRT **не нужны** для выполнения ТЗ; делать только если останется время.

### 13.6. Системные требования (п. 3.1)
- [ ] Замерить на CPU (например, 8 ядер, 16 ГБ RAM) и на GPU: пиковая RAM и VRAM, время,
      размер образа. Записать минимальную (CPU) и рекомендуемую (GPU ≥ 8 ГБ VRAM) конфигурации.

- FastAPI: https://fastapi.tiangolo.com/ ; видео FastAPI + Docker: `data/materials.md`, п. 15
- Про детерминизм в PyTorch: раздел Reproducibility в документации PyTorch

## 20. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Мало примеров отдельных нарушений | высокая | модель анатомии + правила; бесплатные метки с внешних DXA и синтетика из КТ; ручная разметка — только недостающего; метрики по блокам |
| Синтетика из КТ не похожа на DXA (доменный разрыв) | высокая | критерий «идём / не идём» по каждому нарушению; синтетика — только предобучение; аугментации; решение по OOF на реальных данных |
| Внешние данные ухудшают модель или «подсказывают» не то (другой аппарат, контраст, разметка на снимке) | средняя | абляция «с / без» с ДИ; удаление нарисованных линий перед обучением; Grad-CAM |
| Лицензии внешних данных (NC, не указана) | средняя | вопрос организатору 19.8; список данных и лицензий в README и «ограничениях»; для внедрения — переобучение без NC |
| Данные на Aldan-3 недоступны другим участникам / кластер занят | средняя | открыть доступ через администраторов (общий каталог в `/projects/`); MVP без внешних данных; маленькие модели можно учить на CPU |
| Утечка между выборками | средняя | разбиение по пациентам, почти-дубли, кластерный бутстрэп |
| Нет PixelSpacing (H2) | высокая | цепочка калибровки 11.4, вопрос организатору, флаг способа в отчёте |
| Скриншоты отчётов вместо снимков (H1) | средняя | шаблоны по аппарату, OCR только для области |
| Разные аппараты в закрытом тесте | средняя | аугментации контраста, метрики по аппаратам, честные «ограничения» |
| Переходные позвонки и сколиоз ломают нумерацию и угол | средняя | флаги уверенности, отдельные примеры в анализе ошибок |
| Субъективные границы (4–6°, «слегка деформирован») | высокая | согласие разметчиков, зона «сомнительно», пороги ТЗ не подгонять |
| Лицензия AGPL мешает внедрению | низкая для конкурса | стек MIT/Apache на финале или явное указание |
| Контейнер падает на машине организатора | средняя | `--network none`, «чистая машина», тесты плохих файлов, CPU-фолбэк |
| Не успеваем | средняя | приоритеты: MVP → все обязательные коды → сервис и документация → оверлей → SR → веб → автокоррекция |
