Ниже — дефекты, которые видны в приведённых версиях файлов. Сначала те, которые способны молча испортить или потерять данные.

# 1. Критические: молчаливая потеря или порча данных

## `foreign_annotator.py`

### 1.1. Любой открытый снимок автоматически становится `done`, даже без разметки

**Места:**

- `Application.blank()` возвращает `"state": "done"`.
- JS `setInterval(()=>{if(active())enqueue()},15000)`.
- `window.onblur=()=>{account();enqueue()}`.
- `Application.validate()` не требует рамок для `state == "done"`.

**Проявление:**

Через 15 секунд после открытия снимка пустая запись сохраняется как завершённая:

```json
{
  "state": "done",
  "boxes": []
}
```

Это происходит даже:

- на положительном снимке `y_foreign == 1`;
- если пользователь вообще ничего не делал;
- если изображение не прочиталось;
- если пользователь просто переключил вкладку.

Снимок учитывается в прогрессе как размеченный. В результате можно получить большое число ложных «готовых» положительных снимков без рамок.

**Исправление:** черновик не должен иметь `state=done`. Нужен либо отдельный `draft`, либо отсутствие записи до явного действия. Для `y_foreign == 1` завершение без хотя бы одной рамки типа `object` должно требовать отдельного явного подтверждения/состояния.

**Миграция существующих данных:** автоматически отличить намеренно пустой `done` от автосохранённого уже невозможно. Нужно:

1. сделать резервную копию;
2. вывести на повторную проверку как минимум все записи `state=="done" && boxes==[]`;
3. особенно считать подозрительными `y_foreign==1`;
4. вероятные автозаписи удалить из `images`, чтобы они снова стали неразмеченными.

### 1.2. Ответ старого PUT заменяет более новое локальное состояние `ann`

**Место:** JS `enqueue()`:

```js
.then(saved=>{
   saveOK=true;ann=saved;current.annotated=true;showError("");
})
```

**Проявление:**

Если пользователь быстро делает несколько изменений:

1. изменение A ставится в очередь;
2. до ответа сервера делается изменение B и тоже ставится в очередь;
3. приходит ответ на A и выполняется `ann=saved`, заменяя текущий объект старым снимком A;
4. следующее действие C делается уже поверх старого A;
5. C ставится после B и может затереть B на сервере.

То есть очередь HTTP-запросов сохраняет порядок запросов, но присваивание `ann=saved` создаёт гонку в клиентском состоянии.

**Исправление:** не заменять `ann` ответом старого сохранения либо применять ответ только при совпадении UID и локальной версии/revision. Нужен монотонный номер ревизии.

---

### 1.3. Комментарий не синхронизируется при смене снимка

**Место:** `load(item)` после загрузки `ann`; отсутствует присваивание:

```js
$("comment").value = ann.comment;
```

**Проявление:**

Textarea продолжает показывать комментарий предыдущего снимка. При первом вводе этот текст записывается уже в текущий снимок:

```js
$("comment").oninput=()=>mutate(()=>{ann.comment=$("comment").value});
```

Кроме того, существующий комментарий текущего снимка пользователю вообще не показывается.

Это прямое перенесение комментариев между изображениями.

---

### 1.4. При загрузке следующего снимка некоторое время используется `ann` предыдущего

**Место:** начало `load(item)`:

```js
current=item;
...
imageObj=null;
...
ann=await api(...)
```

Перед запросом `ann` не обнуляется и нет флага `busy`.

**Проявление:**

Пока идёт GET аннотации, `current` уже относится к новому снимку, а `ann` — ещё к старому. В этот промежуток доступны:

- горячие клавиши;
- комментарий;
- skip/empty;
- периодическое сохранение;
- действия на canvas.

Если размеры и метки совместимы, старая разметка может быть сохранена под UID нового снимка. В иных случаях пользователь получает ошибку сохранения.

**Исправление:** перед сменой `current` ставить `busy=true`, `ann=null`; разрешать действия только после полной загрузки аннотации и изображения.

---

### 1.5. Быстрые переходы запускают несколько `load()` без сериализации

**Места:** `go()`, обработчики Next/Prev, `load()`.

Нет `navigating`/`busy`, а `go()` не ожидает уже выполняющийся `load()`.

**Проявление:**

Несколько быстрых N/P могут создать параллельные загрузки. Более медленный старый запрос способен завершиться позже нового и заменить:

- `current`;
- `index`;
- `ann`;
- `imageObj`.

В итоге изображение, UID и аннотация могут оказаться от разных переходов.

---

### 1.6. При изменении выборки код молча удаляет старые аннотации

**Место:** `Application.__init__()`:

```python
for uid in list(self.data["images"]):
    if uid not in self.items:
        del self.data["images"][uid]
```

**Проявление:**

Если запустить тот же `--annotator`:

- с другой `--part`;
- с изменённым CSV;
- после временной ошибки фильтрации;
- с другой подвыборкой,

записи вне текущей выборки удаляются из памяти. При следующем сохранении весь JSON записывается уже без них.

Особенно опасно переключение `--part 1` / `--part 2` с одним выходным файлом.

**Исправление:** никогда не удалять неизвестные записи автоматически. Либо отказ запуска при несовпадении fingerprint выборки, либо хранить их неизменёнными.

**Миграция:** если удалённый файл уже перезаписан, восстановление возможно только из резервной копии/экспорта. Атомарная замена предыдущую версию не сохраняет.

---

### 1.7. Нет межпроцессной блокировки выходного JSON

**Места:** `Application.__init__()`, `main()` — `*.lock` отсутствует.

**Проявление:**

Два процесса с одинаковыми `--out` и `--annotator` загружают одну исходную копию. Каждый атомарно записывает собственную версию целиком. Последний процесс стирает изменения первого, даже если они размечали разные снимки.

`threading.RLock` защищает только потоки одного процесса.

То же опасно при `--reset`: активный старый сервер может после переименования backup снова создать основной файл и конкурировать с новым сервером.

---

### 1.8. Две вкладки одного сервера могут перезаписывать один снимок

**Место:** `Application.save()`; клиент не передаёт revision/version.

**Проявление:**

Обе вкладки получают одну версию аннотации. Последний PUT полностью заменяет запись данного UID. Никакого 409 при устаревшей версии нет.

Для разных UID серверное слияние обычно сохраняет обе записи, но для одного UID действует last-write-wins.

---

### 1.9. Сохранение при закрытии вкладки не гарантировано и предупреждения нет

**Места:**

- `window.onblur=()=>{account();enqueue()}`;
- отсутствует `beforeunload`;
- `fetch` без `keepalive`.

**Проявление:**

При закрытии окна запрос с последними изменениями может быть отменён браузером. Пользователь не получает предупреждения. Особенно вероятно при накопившейся очереди сохранений от ввода комментария.

---

### 1.10. Перезапуск уничтожает исторические `updated` всех загруженных записей

**Место:** `Application.validate()`:

```python
result = self.blank(uid)
...
result.update(..., updated=now_iso())
```

Поле `raw["updated"]` игнорируется.

**Проявление:**

При запуске каждая существующая запись валидируется и получает новое время в памяти. При следующем сохранении нового снимка весь JSON записывается с обновлёнными timestamp старых снимков. История времени последнего изменения теряется.

## `axis_review.py`

### 1.11. При нескольких сохранениях `beforeunload` может не увидеть незавершённую очередь

**Места:**

- `schedule()`;
- `saveIfComplete()`;
- обработчик `beforeunload`.

Проверка сделана по тексту:

```js
if (failed || el("status").textContent === "Сохранение…")
```

Но счётчика pending нет.

**Проявление:**

При быстрых изменениях, например нескольких символах примечания:

1. в очереди находится несколько `/save`;
2. завершается первый запрос и callback пишет `"Сохранено"`;
3. следующий запрос ещё выполняется;
4. пользователь закрывает вкладку;
5. `beforeunload` не предупреждает, потому что текст уже `"Сохранено"`.

Последние изменения могут потеряться.

**Исправление:** отдельный счётчик/флаг pending, уменьшаемый только после завершения каждой задачи.

---

### 1.12. При ошибке сохранения нет повторной отправки, перезагрузка теряет локальные изменения

**Место:** `schedule()`:

```js
failed = true;
...
"Проверьте сервер, затем перезагрузите страницу."
```

После `failed=true` все следующие задачи просто пропускаются:

```js
if (failed) return;
```

**Проявление:**

Если диск временно недоступен или произошёл сетевой сбой, интерфейс предлагает перезагрузку, но несохранённый ответ существует только в JS и после перезагрузки исчезнет.

Это не повреждает уже атомарно сохранённые 60 ответов, но может потерять текущий ответ/последние правки.

---

### 1.13. Нет fingerprint исходного индекса и конфигурации очереди

**Место:** `ReviewApp.__init__()` при открытии существующего файла проверяет только:

```python
reviewer
seed
unknown uid
```

Не проверяются:

- исходные метки `y_axis`;
- пути/идентичность DICOM;
- `study`;
- `--part`;
- `--duplicates`;
- полный состав и порядок очереди.

**Проявление:**

Можно продолжить старый JSON с:

- теми же UID, но изменёнными исходными метками — отчёт посчитает κ против новых меток;
- теми же UID, но другими DICOM-файлами;
- другим числом/набором скрытых повторов;
- иной структурой исследований, меняющей кластерный bootstrap.

Ошибки не будет.

**Исправление:** сохранять fingerprint зафиксированного индекса и параметров протокола.

**Миграция 60 ответов:** ответы менять не нужно. В существующий файл или sidecar следует добавить fingerprint именно того CSV и параметров, с которыми ответы реально собирались. Если исходный индекс неизвестен, его надо восстановить/зафиксировать до продолжения; считать отчёт против произвольного текущего CSV нельзя.

---

### 1.14. Изменение `--duplicates` может переопределить смысл существующих `uid#2`

**Место:** генерация повторов в `ReviewApp.__init__()` и проверка существующего файла.

**Проявление:**

Количество повторов не хранится в файле. При другом `--duplicates` выбирается другой набор источников, но старые ключи `uid#2` принимаются, если базовый UID есть в индексе. Некоторые старые повторы могут исчезнуть из новой очереди, а новые — появиться.

Отчёт при этом продолжает учитывать старые `#2`, смешивая разные варианты протокола.

---

### 1.15. Разделитель `#2` не запрещён в исходном UID, а `slot_uid()` разбирает его слишком широко

**Места:**

```python
def slot_uid(key):
    return key.split(REPEAT_SUFFIX)[0]
```

`read_index()` не запрещает `#`/`#2`.

**Проявление:**

UID, содержащий `#2` внутри или заканчивающийся на `#2`, будет принят за скрытый повтор или обрезан до другого UID. Возможны коллизии ключей и неверное сопоставление повторов.

Для стандартного DICOM SOP UID это обычно не встречается, но формат кода это не гарантирует.

## `hip_annotator.py`

### 1.16. Нет межпроцессного `*.lock`

**Места:** `Application.__init__()`, `main()`.

Внутренняя `revision` защищает вкладки одного сервера, но не два отдельных процесса.

**Проявление:**

Два сервера открывают один JSON с одинаковой revision. Каждый успешно пишет атомарно свою копию, и последний процесс стирает работу другого. Никакого конфликта между процессами не будет.

Это особенно опасно, поскольку интерфейс прямо предупреждает только про одну вкладку, но технически не запрещает второй процесс.

---

### 1.17. Шестая точка автоматически превращает черновик в `done` без нажатия N

**Места:**

```js
function mode(){
 if(ann.state==="skipped")return "skipped";
 return names.every(k=>ann.points[k])?"done":"draft";
}
```

и каждый `mutate()` вызывает:

```js
queueSave();
```

**Проявление:**

После задания шестого состояния/точки обычное автосохранение немедленно пишет запись в `images` как `done`. Клавиша N для завершения не нужна, хотя инструкция говорит:

> N завершает снимок, если заданы все шесть точек.

Пользователь может рассчитывать ещё проверить точки или комментарий, но прогресс уже считает снимок завершённым.

Это также позволяет быстро отметить шесть состояний и случайно получить `done` без явного подтверждения.

**Исправление:** обычное автосохранение должно сохранять `draft`; `done` — только при явном N/кнопке завершения. Для ранее завершённой записи можно отдельно сохранять её статус при редактировании.

---

### 1.18. Редактирование комментария у `skipped` снимает пропуск и может сделать снимок `done`

**Места:**

```js
function mutate(fn){
 ...
 fn();
 delete ann.state;
 ...
 queueSave();
}
```

и `mode()` выше.

**Проявление:**

Любое изменение пропущенной записи, даже только комментария:

- удаляет `ann.state == "skipped"`;
- если в записи есть все шесть точек — сохраняет её как `done`;
- иначе переводит в draft.

Флаг пропуска теряется без явного действия пользователя.

---

### 1.19. D и D₂ не пересчитываются при изменении источника направляющих

**Места:** `guide()`, `level()`, `put()`.

Привязка выполняется только в момент установки точки:

```js
if(key==="D"||key==="D2"){
  ...
  q.y=y;
}
```

**Проявление:**

Если после постановки D/D₂ пользователь:

- передвинул T;
- изменил состояние T;
- изменил B1/B2, используемые как fallback;
- заменил источник с T на середину B1/B2,

линии на экране переместятся, а сохранённые `D.y`/`D2.y` останутся на старом уровне. Валидация сервера это не проверяет. В результате JSON содержит точки, не лежащие на показанных направляющих.

Это молчаливая геометрическая порча.

**Исправление:** при изменении источника либо автоматически пересчитывать D/D₂ с явным уведомлением, либо инвалидировать их и требовать повторной постановки. На сервере проверять допустимое отклонение от вычисленной линии.

**Миграция:** для существующих записей вычислить ожидаемые уровни:

```text
D:  guide_y + 20 / 0.606
D2: guide_y + 50 / 0.606
```

и сформировать список расхождений. Автоматически переписывать координаты рискованно: неизвестно, двигался ли источник после осознанной постановки. Лучше повторно проверить отмеченные снимки.

---

### 1.20. Fingerprint не включает путь или содержимое DICOM

**Место:** расчёт `fingerprint`:

```python
digest(r["uid"], r["study"], rows, cols, side, y_pos)
```

**Проявление:**

Если CSV сохраняет те же UID и размеры, но `path` начинает указывать на другой файл, старые точки будут приняты как относящиеся к новому изображению.

Лучше включать как минимум нормализованный путь, а надёжнее — хеш файла или проверенный SOPInstanceUID из самого DICOM.

---

### 1.21. Метка `y_pos` всё-таки утекает в API браузера

**Места:**

- `blank()` включает `"y_pos": item["y_pos"]`;
- `view()` возвращает всю `annotation`.

Комментарий говорит:

```python
# Не показываем метку ... в UI.
```

Но `/api/item/<index>` содержит её внутри `annotation`.

**Проявление:**

В интерфейсе метка не нарисована, однако она видна в DevTools/Network и доступна JS. Если разметка должна быть слепой, слепота нарушена.

---

### 1.22. Скрытые повторы частично раскрываются порядком и номером показа

**Места:**

```python
order.extend(uid + "#2" for uid in base[:5])
```

и UI:

```js
`Показ ${index+1} из ${current.total}`
```

**Проявление:**

Последние пять показов гарантированно являются повторами первых пяти. Пользователь видит позицию. Зная протокол или заметив структуру, он может сознательно воспроизводить предыдущий ответ, что искажает оценку повторяемости.

Сохранение и отчёт основные/повторы разделяют правильно; дефект именно в скрытости.

# 2. Серьёзные дефекты, мешающие работе или ревизии

## `foreign_annotator.py`

### 2.1. После `skipped` или `empty_confirmed` нельзя нормально вернуться к рамкам

**Места:** рисование не меняет `ann.state`, а сервер запрещает рамки в этих состояниях:

```python
if state == "empty_confirmed" and boxes: raise
if state == "skipped" and boxes: raise
```

**Проявление:**

Пользователь возвращается к пропущенному/пустому снимку и рисует рамку. Клиент оставляет старое состояние, сервер отклоняет сохранение. Кнопки «вернуть в работу» нет.

---

### 2.2. Кнопка U не меняет `sure` выбранной рамки вопреки инструкции

**Место:**

```js
$("sure").onclick=()=>{sure=!sure;render()};
```

Она всегда меняет только значение для новых рамок.

При этом инструкция говорит:

> U помечает выбранную рамку как неуверенную.

Клавиатурная U действительно меняет выбранную рамку, а кнопка — нет. Пользователь может думать, что снял уверенность с существующей рамки, хотя изменил только будущие рамки.

---

### 2.3. Клампинг новой рамки искажает геометрию при начале drag вне изображения

**Место:** `clampBox()`.

Сначала клампится `x/y`, но ширина/высота остаются вычисленными по неклампленным концам.

**Пример:**

Drag от `x=-100` до `x=100` создаёт примерно:

```text
x=0, w=200
```

вместо видимой части шириной 100 пикселей.

Drag полностью вне изображения способен создать узкую рамку на границе. Нужно клампить обе конечные точки, затем вычислять `x/y/w/h`.

### 2.6. Атомарная запись не fsync’ит каталог

## `axis_review.py`

### 2.7. `region` обязателен, но вообще не используется для отбора

**Место:** `read_index()`.

Колонка входит в `required`, однако каждая строка с непустым `y_axis` добавляется независимо от `region`.

**Проявление:**

Если `y_axis` заполнен не только для нужных снимков позвоночника, в слепой пересмотр попадут бедро или другие регионы. Пользователь увидит нерелевантное изображение, а отчёт включит его в κ.

### 2.8. Устаревший `.lock` полностью блокирует работу

**Место:** `run_review()`.

Это в основном ожидаемая защита, но lock содержит PID и при этом код не проверяет, жив ли этот PID.

**Проявление:**

После `kill -9`, падения Python или перезагрузки файл остаётся. Следующий запуск требует ручного удаления.

Безопаснее при старте прочитать PID, проверить его существование и только затем предложить удалить stale lock. Автоматически удалять lock без проверки нельзя.

### 2.9. Две вкладки не портят данные, но взаимно ломают сессию

**Место:** один глобальный `position`, `visit`, `image_token` в `ReviewApp`.

**Проявление:**

Открытие/навигация во второй вкладке меняет `visit` для первой. Сохранение первой получает «устаревшая сессия снимка» и интерфейс переходит в `failed`.

Это скорее безопасный отказ, чем порча, но пользователю придётся перезагружаться и можно потерять текущий локальный ответ.

# 3. Координаты и направляющие

## Что в пересчёте сделано правильно

В обоих canvas-инструментах базовые преобразования согласованы:

```js
native: x = (screenX - ox) / zoom
screen: x = nativeX * zoom + ox
```

`devicePixelRatio` используется только для backing store canvas, а transform возвращает рисование к CSS-пикселям. Поэтому DPR сам по себе координаты не искажает.

Панорамирование и зум вокруг указателя также используют правильную обратную точку.

## `foreign_annotator`

Основной геометрический дефект — описанный выше `clampBox()`: нужно клампить концы отрезка, а не отдельно начало и размер.

При изменении размера окна сохранённые координаты не меняются, что правильно. Текущий вид не центрируется автоматически, но это не порча координат.

## `hip_annotator`

Формулы для миллиметров внутренне согласованы с объявленными константами:

```text
x_mm = dx * 0.600
y_mm = dy * 0.606

D_y  = guide_y + 20 / 0.606
D2_y = guide_y + 50 / 0.606
```

То есть используются именно 0,606 мм на вертикальный пиксель. Главный дефект — не формула, а отсутствие повторной привязки после изменения T/B1/B2.

Отдельно нужно документально подтвердить, что «+20/+50 мм» должны откладываться именно по вертикальной оси изображения. Если по протоколу это расстояние вдоль оси диафиза, текущие горизонтальные линии принципиально неверны: код не оценивает направление диафиза и не строит перпендикулярные ему сечения.

# 4. Скрытые повторы и отчёты

## `axis_review`

Разделение основных ответов и `#2` в отчёте в целом сделано правильно:

- `#2` не входит в основную confusion table;
- межэкспертное сравнение пересекается с `set(records)`, поэтому повторы туда не попадают;
- повтор сопоставляется с основным ответом того же UID.

Недостатки:

1. протокол повторов не зафиксирован fingerprint;
2. разделитель `#2` не запрещён в исходных UID;
3. повторяемость выводится только как число совпадений, без κ или интервала неопределённости. Это не арифметическая ошибка, но метрика ограниченная.

## `hip_annotator`

Основные и повторы в `report()` тоже разделены правильно, поскольку исходные UID запрещают `#`.

Но:

- прогресс `finished` включает и основные, и повторы;
- UI показывает общий номер;
- последние пять повторов структурно раскрыты;
- фиксированные источники плохо работают после `--part`.

# 5. Слепота `axis_review`

В обычных API-ответах явной утечки исходной метки, UID, study, пути, угла или номера строки я не вижу:

- `/enter` возвращает capability-token изображения, а не UID;
- PNG не содержит DICOM metadata;
- browser errors обобщены;
- заголовок страницы нейтрален;
- порядковый номер в HTML не выводится;
- серверные логи URL отключены.

Оставшиеся каналы:

1. **Пиксели самого DICOM.** Защита только организационная через `--clean-pixels-confirmed`; код не удаляет burned-in annotation.
2. **Сохранённый предыдущий ответ** возвращается при повторном посещении. Это нарушает слепоту относительно собственного прошлого ответа, но необходимо для редактирования и не раскрывает исходную метку.
3. **Состав изображений:** `region` не фильтруется, поэтому нерелевантное изображение само может подсказать ошибку формирования выборки.
4. `can_previous` и достижение конца дают приблизительную информацию о позиции, но не UID/метку.

Имена DICOM-файлов и SOP UID в HTML/API изображения не попадают.

# 6. Арифметика отчётов

## `axis_review.py`

Следующие формулы реализованы корректно:

- confusion matrix: строки — исходная метка, столбцы — новая;
- Cohen’s κ:
  \[
  \kappa=(p_o-p_e)/(1-p_e)
  \]
- положительное согласие:
  \[
  2TP/(2TP+FP+FN)
  \]
- изменение доли положительных: `(FP-FN)/n`;
- точный двусторонний Макнемар через удвоенный нижний хвост `Binomial(n, 0.5)`;
- `unsure` и пропуски не превращаются в отрицательные;
- cluster bootstrap выполняется по исследованиям, а пустые `study` не объединяются.

Ограничение bootstrap: вырожденные реплики с неопределённой κ выбрасываются. Код это печатает, но percentile CI тогда условен на «κ определена» и может быть смещён при малой/однородной выборке. Это не скрыто, но такой CI нельзя трактовать как обычный безусловный 95% ДИ.

## `hip_annotator.py`

Расстояние считается корректно с анизотропным масштабом:

```python
hypot(dx * 0.600, dy * 0.606)
```

И заявленная формула повторяемости реализована буквально:

\[
SD=\sqrt{\frac{\sum_i d_i^2}{2n}}
\]

Максимум — максимальное парное евклидово расстояние в мм.

Важно: это RMS/TEM без вычитания систематического сдвига, а не обычное выборочное стандартное отклонение расстояний. Комментарий это честно сообщает.

# 7. Косметические и диагностические проблемы

1. **`foreign_annotator`:** `complete` и `annotated` фактически означают одно и то же, потому что допустимы только конечные состояния. Это маскирует отсутствие настоящего draft.
2. **`foreign_annotator`:** ошибки DICOM скрывают исходное сообщение и показывают только тип исключения. Это затрудняет диагностику неверного path/codec.
3. **`hip_annotator`:** комментарий «Не показываем метку в UI» создаёт ложное ощущение слепоты, хотя `y_pos` есть в API.
4. **`axis_review`:** stale lock требует ручной операции, хотя PID уже записан и может быть использован для диагностики.
5. **`hip_annotator`:** потеря времени при `visibilitychange`: сначала выполняется `last=performance.now()`, а затем `queueSave()` вызывает `account()`, поэтому интервал непосредственно перед скрытием не учитывается. Потеря обычно до периода секундного таймера.
